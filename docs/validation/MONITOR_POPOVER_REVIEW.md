## 2. 待修复问题

### M1 · P1 · 点击其他 App 后监控未关闭

**现象：** 用户报告监控停留；日历正常关闭。

**要求：** 两个弹窗保持相同的临时弹窗交互。点击其他 App、桌面，或通过 Cmd-Tab 切换到其他 App 后应关闭；外部点击正常送达目标 App，不能仅吞掉一次点击。不得把监控变成固定悬浮窗，也不新增“置顶/固定”功能。

**关联风险：** `popoverDidClose` 才将监控面板可见状态设为 false。若窗口未关闭，逐应用采样也可能继续，影响用户要求的低占用。这是代码可解释的风险，尚未实测额外 CPU 消耗或泄漏，不能写成已证实泄漏。

### M2 · P1 · 首次打开后还需点击窗口才能进入预期状态

**现象：** 图一到图二呈现明显外观变化，用户感知需要再点一次。

**要求：** 首次左击菜单栏监控项即进入可操作状态；“查看更多”、滚动等首次交互应直接生效，不能需要先点一下唤醒。点击空白内容区不得成为切换玻璃外观的必要步骤。再次点击同一菜单栏项应关闭该弹窗；点击另一个 CalMon 状态项应关闭当前并打开对应弹窗，最多存在一个业务弹窗。

### M3 · P2 · 监控与日历的材质验收必须覆盖首次打开

**要求：** 保持原生系统材质；两个弹窗在相同背景、系统外观、辅助功能设置和激活状态下，外壳、边框、阴影及内容表面的样式一致。以用户更认可的图二观感作为对照线索，不能仅截取二次点击后的画面宣布通过，也不能用硬编码底色或自绘玻璃掩盖激活状态问题。系统随背景产生的自然颜色变化不算缺陷。

## 3. 当前源码检查：排查线索，不是最终根因

- `CalMon/App/MenuBarController.swift`：两个 NSPopover 均设置 `.transient`，因此“给监控加 transient”本身不是充分修复。
- 两个打开方法目前均直接 `show(...)`，没有在此处显式统一窗口激活与焦点过程；设置窗口另有 `makeKeyAndOrderFront` 与 `NSApp.activate`。
- `CalMon/Calendar/CalendarView.swift` 有 `.focusable()` 和显式 Esc 关闭回调；`MonitoringView.swift` 无对应逻辑。这是行为差异线索，不足以证明它单独导致不关闭，也不能断言监控 Esc 必然失效。
- 需在真实菜单栏点击链路中核验应用激活、弹窗 key window/first responder、失活和关闭通知顺序。只复用展示截图钩子不足以验证首次点击。
- 如确需新增事件观察，必须随弹窗生命周期安装/移除，避免重复注册；禁止新增轮询或为了修补关闭行为申请辅助功能权限。优先系统原生行为，不强制指定未验证的实现方案。

## 4. 修复后的验收清单

每项记录监控/日历结果与证据，未执行明确标注。以单个 Release 实例测试，不用单测通过代替实机交互。

| 场景 | 预期 |
| --- | --- |
| 其他 App 为前台，首次点击状态项 | 弹窗首次出现即为正确状态；无需二次点击激活 |
| 首次点击“查看更多”与滚动 | 一次操作生效；无额外激活点击 |
| 点击面板空白区 | 不重复创建窗口，不意外切换样式 |
| 再次点击同一状态项 | 关闭 |
| 点击另一状态项 | 两面板互斥切换，锚点正确 |
| 点击其他 App 内容区、桌面 | 弹窗关闭，目标正常响应 |
| Cmd-Tab 切换 App | 弹窗关闭 |
| Esc | 两种弹窗都关闭 |
| 关闭后等过一个 3 秒周期 | 逐应用采样停止，迟到任务不重新填充面板状态；基础 CPU/MEM 保持既定设置 |
| 反复开关并切换 App | 不出现残留弹窗、观察者/任务累计 |
| 同背景下记录首次打开、内容点击后状态 | 原生外观一致，无必须二次点击的异常变化 |
